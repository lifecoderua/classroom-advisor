# Architecture

```
┌──────────── collector (home machine; later a microVM) ───────────┐
│ Chrome (dedicated profile, kids multi-logged-in)                  │
│   ↑ Playwright / CDP                                              │
│ session → accounts → To-do lists → assignment details → files     │
└──────────────┬────────────────────────────────────────────────────┘
               │ normalized objects (zod)
┌──────────────▼──────────── core ──────────────────────────────────┐
│ sync: hash/diff → store (SQLite+Prisma, versioned) → domain events │
│ checks: deadline rules │ turned-in heuristics → LLM second pass    │
│ alerts (deduped) → notify: console report, Telegram bot           │
└───────────────────────────────────────────────────────────────────┘
```

For now it's a single TS package with modules under `src/`:

| Module | Responsibility |
|---|---|
| `config/` | `.env` + `config.local.json` (watched accounts, profile dir, provider), zod-validated |
| `collector/` | browser session, account discovery, page/RPC capture, parsers, file fetcher |
| `store/` | Prisma 7 client (better-sqlite3 adapter, DB at `<dataDir>/app.db`) + repositories; JSON stored as strings |
| `sync/` | orchestration: diff, versioning, domain events |
| `checks/` | deadline rules, turned-in heuristics, LLM quality pass, verdict merge |
| `llm/` | `LlmProvider` adapter: `claude-cli` (default), `gemini`, `fake` |
| `notify/` | console digest; Telegram bot (Bot API over fetch) |
| `run/` | `run` loop: cycle orchestration, quiet hours, lock file |
| `cli/` | `doctor`, `accounts`, `recon`, `sync`, `check`, `report`, `run`, `telegram link|test` |

## Accounts

One Chrome profile holds several Google accounts. We list them from the session (`accounts.google.com/ListAccounts` or the account switcher) and address each one with `?authuser=<email>`, which is stable, unlike `/u/N/`, which depends on login order. The **watch list** (which accounts to sync) lives in `config.local.json` (`accounts watch|unwatch <email>`) and is mirrored to `Account.watched` by those commands (when the DB exists) and at the start of every sync.

Session details (`src/collector/session.ts`, `accounts.ts`):
- Playwright `launchPersistentContext(profileDir, { channel })`, headful by default. `channel` is `chromeChannel` / `CA_CHROME_CHANNEL`: `chrome` (default, installed Google Chrome) or `chromium` (Playwright's bundled build, used by the Docker image on arm64). We drop Playwright's `--use-mock-keychain` / `--password-store=basic` defaults: with them Chrome can't decrypt the profile's cookies (macOS Keychain key) and the hand-made login looks gone.
- A live `SingletonLock` (`<host>-<pid>` symlink) in the profile means Chrome is open on it → `ProfileLockedError`.
- Discovery: **POST** `ListAccounts?gpsia=1&source=ChromiumBrowser&json=standard` via `context.request` (shares the profile cookies; GET answers 400), parsed like Chromium does (`[3]` email, `[7]` authuser index, `[14]` signed out); fallback is reading emails off the account chooser page. No accounts → `SessionMissingError` (log in by hand).

## Data sources (see CLASSROOM-INTERNALS.md)

- Pages carry **no data in their HTML**. Everything loads through read-only internal RPCs (`/u/<n>/_/ClassroomUi/data/batchexecute`). Per account we open one Classroom page headless, read the tokens (`WIZ_global_data`), and then **call the RPCs directly** with same-origin `fetch`. This was tested on real data: 170 submissions came back in one call.
- To-do listing: `pONvgf` (paged) + `Zj93ge` (submissions, bucket `[20]`) + `gXtzob` (courses). Details: `tQShAc`, `t51ITc` (materials), `Zj93ge` with the attachments mask, `sLc6hf` (comments). See CLASSROOM-INTERNALS.md for positions.
- Code: `src/collector/classroom/` — `rpc.ts` (batchexecute client, allow-list, Playwright transport, request templates), `todo.ts` (`listTodo` → `AssignmentSummary[]`), `detail.ts` (`AssignmentDetail`), `enums.ts`, `parse-util.ts` (positional accessors + `ParseDriftError`).
- The rpcids are **allow-listed in code** (read-only only). `recon` stays as a fallback and as a way to diagnose drift.
- Files are read through the same session: Docs via `export?format=txt`, Slides as pptx, Sheets as csv, PDFs, Office files and images raw. They're cached by `driveFileId + modifiedAt`.
- File fetcher (`src/collector/files.ts`): `HttpGet` over `context.request` (+ `authuser=`). Docs `document/d/<id>/export?format=txt`, Slides `presentation/d/<id>/export/pptx` (falls back to `export/txt`, without structure, when the pptx download fails, e.g. > 25MB), Sheets `export?format=csv`, everything else `drive.google.com/uc?export=download&id=<id>` (follows the large-file confirm form). PDFs: raw + text via `unpdf`; `contentPath` points at the `.txt`. Office files (pptx/pptm, docx, xlsx) are recognized by their zip contents (`ppt/presentation.xml`, `word/document.xml`, `xl/workbook.xml`), not the mime, and saved with their real extension plus `<stem>.txt` (plain text, what `contentPath` points at) and `<stem>.office.json` (structure summary); legacy binary `.ppt/.doc` stay `.bin`. A `.bin` cached before this is re-examined locally (sync re-selects versioned `.bin` rows; no refetch). A Slides `.txt` with neither `.office.json` nor a `.text-only` marker (written by the text fallback) came from the old text export: it's stale (`isStaleSlidesText`), so sync re-selects it and the fetcher refetches it once as pptx. Images stay as files.
- Office extraction (`src/collector/office.ts`): fflate unzip (each XML part ≤ 32MB) + a small tag scanner, no XML library. pptx: slides in `p:sldIdLst` order; per slide the text (`a:t` per `a:p`), pictures (`p:pic`), shapes (`p:sp`/`p:cxnSp`/`p:graphicFrame`), animation effects (`p:cTn` in `p:timing` with `presetClass` `entr`/`emph`/`exit`/`path`, counted per class) and the transition (first effect element of `p:transition`, e.g. `fade`). docx: text (`w:t`, tabs, breaks), images (`w:drawing`/`w:pict`), tables. xlsx: cell values per sheet via shared strings. Google Slides' pptx export carries the animations. Forms, links, YouTube and videos: metadata only. Google-native files are recognized by Classroom's internal mimes too (`kix` doc, `punch` slides, `ritz` sheet, `freebird` form). Cache `<dataDir>/files/<driveFileId>/<modifiedAt|nomod>.<ext>` (one dir per file, so the LLM gets Read access to just that dir); `nomod` is always refetched. `contentHash` = sha256 of the `contentPath` file. A login redirect/page throws `SessionExpiredError`; other failures (HTTP, HTML instead of file, >25MB, timeout) return `{ ok: false, error }`.

We parse **network responses / embedded init data, not the DOM** (Classroom's CSS classes are generated). The parsers are defensive, and an empty or invalid parse raises `ParseDriftError`, which surfaces as an alert. Silent breakage is the main risk.

## Sync and caching

`src/sync/` (`pnpm cli sync [--account n] [--headful]`, and the first step of every `run` cycle). It opens the profile once (headless by default), mirrors the config watch list to `Account.watched`, discovers the logged-in accounts and, per watched account, opens one Classroom page and runs `syncAccount` over its RPC transport:
1. `listTodo` → summaries plus the full parsed `pONvgf` items (they already carry the instructions and material refs, so no `tQShAc` call is needed). Each summary gets a `summaryHash` (stored on `Assignment`).
2. `pickItems` chooses whose details to fetch: new items, a changed summary hash, open items due within 48h, and a slow full refresh (items not fetched for `fullRefreshDays`, default 7; at most 20 per sync, stalest first). The rest only get `lastSeenAt`.
3. Details (`fetchDetails`): `Zj93ge` with the list mask and the attachments mask, in batches of 100, plus `t51ITc` per item with material refs → `parseAssignmentDetail`. One item failing (drift, RPC error) is counted and skipped (its summary hash isn't stored, so it is retried); a `ParseDriftError` also raises `sync:<accountId>:drift:<rpcid>:<day>`.
4. Store (`applyDetail`): `upsertAssignment` with the normalized payload (`src/sync/normalize.ts`: `instructions`, `dueAt`, `maxPoints`, materials…; `updatedAt` is left out so it doesn't create versions). `status` comes from the To-do bucket (`assigned`, `missing`, `turned_in` incl. done late, `returned` incl. graded, `excused`) and is refreshed even when the hash is unchanged. Materials and the student's files (teacher-annotated copies excluded) go through `syncAttachments` with `isTemplate` / `templateSourceId`. `upsertSubmission` writes a `SubmissionVersion` on a hash change.
5. Events (`Event`, unique `key` → idempotent): `assignment.new:<assignmentId>`, `assignment.updated:<assignmentVersionId>` (payload `{changes: {field: {from, to}}}` over kind/title/instructions/dueAt/maxPoints/materials), and per new submission version `submission.turned_in|returned|unsubmitted:<versionId>` (state transitions; unsubmitted = turned in/returned → reclaimed) and `assignment.missing:<versionId>` (bucket became missing). `comment.new:<commentId>` comes from step 6.
6. Private comments (`src/sync/comments.ts`): `sLc6hf` for every listed non-material item with a submission, 100 submission keys per call (2 calls per account on the real data; a batch whose answer says `hasMore` is split in half and re-fetched). They're swept every sync because a new comment doesn't reliably change the submission's update time (see CLASSROOM-INTERNALS.md). Stored in `Comment` (deduped by `(assignmentId, classroomId)`; an edit updates `text` in place, no new event) with `authorRole` teacher/student, `authorId` and `postedAt`. A comment is **fresh** unless it's stored by the baseline sync, or it's on a baseline item and was posted before `Account.baselineAt`; non-fresh ones are stored with `baseline` set and nothing else. A fresh comment emits `comment.new:<commentId>` (payload `{authorRole, postedAt}`), and a fresh teacher comment raises `comment:<commentId>` (message `Teacher comment on "<title>" (<course>): <text, ≤600 chars>`): `panic` when it asks to redo, fix or attach something (`isRedoRequest`, see Checks), else `alert`. For a redo request whose submission wasn't turned in after it, the message adds a note when the work is past due or due within a day. A fresh teacher comment also re-queues a quality review (see Checks). Comments of items not stored yet (their details failed) are skipped and picked up next sync. A failed call is counted (`stats.comments.errors`); drift raises the usual `sync:<accountId>:drift:sLc6hf:<day>`.
7. Files: for post-baseline items whose submission is turned in or returned, attachments of that assignment (student work and materials) without cached content are fetched with `fetchAttachmentContents`. Videos, links, YouTube and Forms are metadata only. A failed fetch keeps its error in `Attachment.fetchError` (cleared on success or when the file changes), so the checks can say why the work wasn't checked. Then, for the expects-work classifier (#61), `pickMaterialPrefetch` selects teacher materials of kind doc/slides/sheet/pdf/other (`TEXT_CONTENT_KINDS`) never fetched and never failed, of open (not turned in, returned or excused), non-baseline posts posted within `alertLookbackDays` whose current version isn't classified yet, newest first, at most `expectsWorkMaxPerRun` files per account and sync, and fetches them the same way (read-only; contents stay under `<dataDir>/files`).
8. Run log: one `SyncRun` row per account and sync (`ok | session_expired | session_missing | error`, `baseline`, counts as JSON). A `SessionExpiredError` (or an account that isn't logged in) stops that account, raises `sync:<accountId>:session_expired|session_missing:<day>` and never tries to log in. Other accounts still sync. A later successful sync of the account closes (mutes, reason `auto`) its open lost-login alerts, and its `sync:<accountId>:drift:…` alerts too when that run hit no parser drift (`closeSyncAlerts`, #69). The CLI prints one line of counts per account (no titles, names or emails).

**Baseline (alert-flood guard).** The first successful sync of an account (`Account.baselineAt` is null) is the baseline: everything is stored with `Assignment.baseline` / `SubmissionVersion.baseline` / `Comment.baseline` set, no events are emitted, no files are downloaded, and `baselineAt` is set at the end. Baseline items get only the panics (`missing`, `due_soon`), never `untouched_24h` / `no_due_date`, and baseline submission versions are never quality-reviewed (`pendingQualityVersions` skips them). Independently, `untouched_24h` and `no_due_date` apply only to items posted within `alertLookbackDays` (default 14). On the real data (2 accounts, ~350 items) the guard turns ~290 first-run alerts into 3 panics.

Runs are idempotent: running twice gives no duplicate versions, events or alerts.

## Checks

**Deadline rules** (pure, timezone-safe, UTC in storage):
- *alert*: posted more than 24h ago, not turned in, and no sign of work (no student attachment or doc edit).
- *panic*: due in under 24h and not turned in, **or** marked missing.
- No due date → weekly reminder. Material-only posts are ignored.
- Implemented in `src/checks/deadlines.ts` (pure, over a plain `DeadlineInput` snapshot) and `src/checks/evaluate-deadlines.ts` (loads watched, open assignments and calls `raiseAlert`). Excused items never alert. Baseline items get only the panics, and `untouched_24h` / `no_due_date` need the item to be posted within `lookbackMs` (`alertLookbackDays`, see Sync). Codes: `untouched_24h` (alert), `due_soon` / `missing` (panic; overdue counts as missing), `no_due_date` (info, after 7 days). Dedupe key `deadline:<assignmentId>:<code>`, plus `:<ISO week>` for `no_due_date` so it re-fires weekly. A panic suppresses `untouched_24h` in the same run. Boundaries are strict: exactly 24h is not yet late.

**Expects work?** (#61, D21; `src/checks/expects-work.ts`, prompt `src/checks/prompts/expects-work.v3.md`). Many posts are lesson-schedule entries: `assignment` kind, usually no due date, a description that is only a Zoom/Meet invite. They would get `untouched_24h` and later `no_due_date` for nothing. So each `AssignmentVersion` can carry an expects-work verdict (`expectsWork` `yes|no|unclear`, `expectsWorkReason`, `expectsWorkSource` `llm:<provider>|skeleton`, `expectsWorkAt`, `skeletonHash`):
- **Lazy.** `evaluateDeadlines` (with `expectsWork: {provider, maxPerRun, readText, log}`, passed by the `run` cycle) first finds the open assignments whose current (latest) version is unclassified and whose reminder (`untouched_24h`, `no_due_date`) would fire now, most recently posted first, and classifies those versions; then it runs the pure rules with the verdict in `DeadlineInput.assignment.expectsWork`. Assignments that never reach a reminder (baseline, outside the lookback, covered by a panic) cost nothing. A version is classified once; a content edit creates a new version, which is classified again when its reminder would fire.
- **Input.** Title, description (≤ 3k chars) and the teacher's attachments from the version payload (title, kind, and the cached text when the file was downloaded, else `contentUnavailable: true`; ≤ 3k chars of text together, water-filled). Through `LlmProvider.generate` (see LLM adapter); answer `{expectsWork, reason}` (reason: one short English sentence, operator-facing only). The prompt (`expects-work.v3`): any instruction to do something, even a short one with the details only in an attachment ("розв'язати", "виконати", "solve", page or exercise numbers), is `yes`; recommended or optional-sounding homework ("рекомендовано для виконання вдома", "за бажанням") is `yes` too; `no` only for a bare call invite or schedule entry with no task hint; with an unreadable attachment that can hold tasks (a deck, doc, PDF, file, form) and an ambiguous text, `unclear`, never `no`; attached videos alone (watched, not done) don't make a post `unclear`: a call invite + lesson topic + reference videos is `no` (#69).
- **Attachment content.** The homework of a lesson post often sits only in an attached deck or doc (e.g. a Math post "Самостійно розв'язати приклади" + a pptx), but sync used to download files only for turned-in work. Sync now also prefetches (`pickMaterialPrefetch`, see Sync step 7) the text-bearing teacher materials of the classifier's candidates. A version with such a material not downloaded or tried yet is left unclassified (`awaiting`, reminders as before) until sync has fetched it. **Safety net** (`safetyNet`, deterministic): a `no` is stored as `unclear` (reason prefixed `[no -> unclear: attachment content not available]`) when any material other than a call link (Zoom, Meet, Teams) or a video (YouTube, `video/*`) has no readable text: a failed download, an image, a link.
- **Skeleton cache.** `normalizeSkeleton` lowercases and masks what changes from week to week: URLs → `<url:host>` (the host stays, so a call invite and a worksheet link differ), clock times → `<time>`, month and weekday names (en/uk/ru) → `<date>`, every word that contains a digit (dates, meeting ids, passcodes, class names like `6a`) → `<n>`, whitespace collapsed. `skeletonHash` = sha256 of the normalized title and description plus the sorted attachment keys (`hash:<contentHash>`, else `id:<driveFileId|url>`). If an earlier version of the same account with that hash has an LLM `yes`/`no`, it's reused with source `skeleton` and no call (also when the run's budget is used up). `unclear` is never reused. A weekly invite that only changes time, topic number, meeting id and passcode costs one call in total; a topic that changes in words is a new skeleton.
- **Budget.** At most `expectsWorkMaxPerRun` (`CA_EXPECTS_WORK_MAX_PER_RUN`, default 20) LLM calls per run (failures count); the rest stays unclassified and keeps its reminders this run, so the first run on an existing DB doesn't burst. A failed call stores only the skeleton hash and is retried next run.
- **Effect.** `no` suppresses `untouched_24h` and `no_due_date` for that version (`deadlineAlerts` stays pure); `missing` and `due_soon` are never suppressed. Open reminders of an assignment whose current version is `no` are muted with `muteReason: no_work_expected` (and `sentAt` when unsent). If a later version fires the reminder again (an edit added homework, or its verdict is unknown), that muted alert is revived as a fresh unsent alert. `unclear` keeps the reminders but makes `untouched_24h` low-noise (`info`, 🔵 in the digest) instead of an attention alert (#69); `yes`, an unknown verdict and a failure keep the `alert` level. When the prompt changes in a way that should revisit old verdicts, a migration clears them (`expects-work.v3` cleared the stored `unclear` verdicts).
- **Silent.** Nothing about `no` posts goes to the digest: `no_work_expected` mutes aren't counted in "Closed automatically"; `report --all` marks such alerts "(no homework in the post)". The `run` log prints one count line per cycle (`expects-work: N llm, N skeleton, N failed, N deferred, N awaiting files; N reminder(s) muted, N revived`), no titles.
- Opt-in live prompt check: `CA_LLM_IT=1 pnpm test expects-work.integration`.

**Turned-in quality**, where the core problems are wrong or unchecked work and missing or partial attachments:
1. Heuristics produce *signals* with confidence, not verdicts: `no_attachments`, `fewer_attachments_than_expected`, `template_unchanged`, `empty_or_tiny_doc`, `kind_hint` (quiz/online test/link). Attachments the review can't read are skipped (see *Not checked automatically* below).
   Zero attachments is often valid (a lesson with no homework, or an online test scored elsewhere), so signals alone rarely escalate. Only clear-cut cases do, such as a 100% unchanged template.
   Implemented in `src/checks/heuristics.ts` (pure `turnedInSignals(TurnedInInput)` → `{signals, directVerdict?}`, signals shaped like `ReviewInput.signals`) and `src/checks/evaluate-heuristics.ts` (loads one `SubmissionVersion`: current attachments, kind from mime, instructions from the latest assignment payload's `instructions`/`description`, text via an injected reader; `cachedTextReader(dataDir)` reads cached `.txt/.csv/.md` exports; `cachedOfficeReader(dataDir)` adds the `.office.json` structure as `office`). Details:
   - `no_attachments`: base 0.5; up for upload words (uk/en stems: `прикріп`, `надішл`, `фото`, `виконай`, `зошит`, `attach`, `submit`, `photo`…) or a template; down for quiz/online test, link-only materials, `question` posts, empty posts.
   - `fewer_attachments_than_expected`: fewer than templates (0.6) or than parts in the instructions ("3 фото", "2 pages", numbered list; 0.3, since several parts often fit in one file).
   - `template_unchanged`: word 3-shingle Jaccard ≥ 0.98 against any material text (0.8; ≥ 0.999 → 0.99). Direct `panic` only when every attachment is an identical copy of a template with ≥ 5 words. When both have a structure summary and the copy adds slides, pictures, shapes, animation effects or transitions (`structureAdded`), it's only a 0.3 hint with those additions and never a direct panic (e.g. "add animation effects" to a template).
   - `empty_or_tiny_doc`: fewer than 15 own words (template words subtracted as a multiset), or a 0-byte file. Drops to 0.3 (below the warn threshold) when the file has pictures, animation effects or transitions of its own.
   - `kind_hint`: `material` (short-circuits), `quiz` (quiz kind or Form material), `online_test` (keywords: `тест`, `онлайн`, `naurok`, `vseosvita`, `kahoot`…), `link_only`.
2. An LLM second pass gets the instructions, materials, student work (text + images, or the `unreadable` reason) and the signals, and returns `{verdict ok|warn|panic, addressesAssignment, missingParts[], issues[], summaryForParent, confidence, unverifiable[{what, why}]}`. The audience is kids in grades 1-6 (ages 6-12). Feedback is written in the assignment's language.
3. Merge → `CheckResult` → `Alert` (dedupe key `quality:<submissionVersionId>`).
   Implemented in `src/checks/quality.ts` with the versioned prompt `src/checks/prompts/review.v5.md` (`REVIEW_PROMPT_VERSION`, stored as `findings.promptVersion`; v5 adds: recommended or optional-sounding homework, "рекомендовано для виконання вдома", is required work, to be done fully, #61):
   - `buildReviewInput` (pure): text budget of 24k chars (instructions ≤ 4k; 60% of the rest to the student's work, then materials, water-filled so short texts stay whole, truncation marked), student image paths, signals, `locale` (the digest language `digestLang`: the model writes `summaryForParent`, `missingParts`, `issues` and `unverifiable` in it, whatever language the assignment is in), and `comments`: the latest 10 private comments (`REVIEW_COMMENTS`, oldest first, `{author, postedAt, text}`) within their own 4k-char budget. The prompt treats a teacher's redo/attach request that the work doesn't address as at least `warn`; `applyRedoFloor` enforces it in code (see re-review below).
   - Office files and Slides in the review input: their text with `[slide N]` / `[sheet name]` headers plus a `structure` string (totals, then one line per slide: pictures, shapes, animations by class, transition; ≤ 4k chars, outside the text budget). The prompt tells the model this structure is read from the file and reliable, so it checks animation/picture tasks itself instead of asking the parent.
   - `mergeVerdict`: a heuristic direct panic wins; an LLM panic with confidence < 0.5 becomes warn; a provider failure falls back to the heuristics-only verdict for the merge result (`heuristicVerdict`: direct verdict, else warn on a problem signal with confidence ≥ 0.6).
   - `reviewSubmission(db, versionId, provider, readText, now, {imagePathOf, readOffice})`: loads via `loadTurnedInInput` (now also course name, due date and cached image paths via `cachedImagePath`), stores a `heuristic` CheckResult (once) and an `llm:<provider>` one (verdict = merged verdict, findings `{promptVersion, output, merge}`), and raises the alert for warn (`alert`) / panic (`panic`) with the parent summary. Skips when this provider's result exists. On provider failure it stores no LLM result (the next run retries) and raises nothing, except a heuristics-only `quality:<id>` panic (marked as such) when the heuristics have a direct panic. Failures are counted per provider in the `heuristic` result's `findings.llmFailures`; at 3 it raises `quality:<id>:llm-failed` (`alert`: the automatic review couldn't run).
   - **Re-review on a new teacher comment (#44).** Every `llm:*` CheckResult stores `throughCommentId`: the highest `Comment.id` of the assignment when it ran (comment ids grow with insertion, so this is "what the review had seen"). A fresh (non-`baseline`) teacher comment with a higher id re-queues the latest version: `reviewSubmission` runs again with the comments in the input and stores another `llm:<provider>` result (`findings.trigger = {commentId}`, the latest new teacher comment), so one comment (or several arriving together) gives at most one re-review. Student and baseline comments never re-queue, and a comment already there at the first review is covered by it. The re-review alerts as `quality:<id>:c<commentId>`, and only when the verdict is worse than the previous result's (ok → warn, warn → panic): the comment's own `comment:<id>` alert already carries the news, so an unchanged verdict stays quiet. A failed re-review counts failures under `llm:<provider>:c<commentId>` (alert `quality:<id>:c<commentId>:llm-failed` at 3) and doesn't repeat the heuristic panic. The console shows the latest result.
   - **Redo requests** (`src/checks/redo.ts`): `isRedoRequest` matches word-start stems in Ukrainian, Russian and English (`перероб`, `дороб`, `виправ`, `прикріп`, `додай`, `передел`, `додела`, `исправ`, `прикреп`, `добав`, `redo`, `fix`, `attach`, `resubmit`, `upload`, `missing`, …; case-insensitive; `виправлен…`/`исправлен…` "corrected" excluded). `openRedoRequest` is the snapshot's latest teacher comment when it is such a request and the work wasn't turned in after it (a later teacher comment supersedes it). An open request lifts an `ok` LLM verdict to `warn` (`applyRedoFloor`, noted in `merge.notes`), and when the work is past due or due within a day the quality alert ends with a note saying so.
   - CLI: `check quality [--submission-version <id>] [--provider <name>]` runs it over `pendingQualityVersions` (latest turned-in/returned, non-baseline version per submission of watched accounts without a result from that provider, or with a fresh teacher comment newer than its results' `throughCommentId`). The `run` cycle reviews the same set right after sync.
   - Opt-in live prompt check: `CA_LLM_IT=1 pnpm test quality.integration` (synthetic Ukrainian homework, `CA_LLM_IT_VERBOSE=1` prints the outputs).
4. **Not checked automatically** (#43, D16). Complex formats and checks may be skipped, but never silently: they're reported with a reason as "check by hand".
   - `unreadableReason` (`src/checks/readability.ts`, pure) marks an attachment unreadable unless it has text, an image or an Office structure. Reasons, in order: PDF with no text layer (a scan), video/YouTube ("needs watching"), audio by mime or extension ("needs listening"), Google Form, external link (with its host), legacy `.ppt`/`.doc`/`.xls` (by mime or title; the collector keeps them as `.bin`), the stored `fetchError` (too large with the size in MB, no access with the HTTP status, extraction failed, other download errors), not downloaded, unreadable cached text, unsupported image format (`.bmp`, `.svg`…), any other format (with the title's extension). An empty Google Doc is readable: it's empty work, a signal. `loadTurnedInInput` sets `unreadable` on materials and student attachments.
   - The heuristics skip unreadable attachments (no signals for them); the LLM input carries the reason as `attachments[].unreadable`.
   - **Nothing readable** (something attached, all of it unreadable): the LLM isn't called. With no content it could only repeat the instructions; "was an upload expected" matters only when nothing is attached, which still goes to the LLM. `unreadableVerdict`: the heuristics' warn/panic if any, else `unchecked`. The result is stored as the `llm:<provider>` CheckResult (verdict `unchecked`, findings `{promptVersion, merge, unchecked}`) so the version isn't picked up again.
   - **Partly readable**: the readable part is reviewed normally; the unreadable attachments are listed with their reasons.
   - **What the LLM can't verify**: `unverifiable: [{what, why}]` in the output (required, may be empty; e.g. a score on Naurok, a reading that needs listening, paper-notebook work not asked to be photographed). The prompt says to list such parts there instead of a `warn` asking the parent to check, not to repeat attachments already marked `unreadable`, and that the verdict covers what could be checked.
   - Alerts: the unchecked parts (unreadable attachments + `unverifiable`) are stored as `findings.unchecked`. With a warn/panic they're appended to the `quality:<id>` alert ("Not checked automatically: …"); otherwise they raise `quality:<id>:unchecked` (level `info`, `Check by hand: "<title>" (<course>): "<file>": <reason>; …`), one per submission version. No separate alert when there's a warn/panic.
   - A re-review on a new teacher comment (#44) carries the same `unchecked` parts and `unverifiable` handling; its check-by-hand alert is keyed `quality:<id>:c<commentId>:unchecked`.
   - **Retry on temporary causes**: an `unchecked` result whose reasons are all temporary (a fetch error other than too large / extraction failed, or "not downloaded") is retried by `pendingQualityVersions` on later runs, at most `UNCHECKED_RETRIES` (3) times (counted as `unchecked` results of that provider), then it stays `unchecked` and only then raises the check-by-hand alert. Such results store `findings.retryable: true` (`reviewSubmission` returns `retryPending`). Legacy formats, audio/video, too-large files and the like are final. A new submission version is always reviewed.

Later, a thin **user-rules** layer can adjust signals and verdicts, e.g. "online tests with no attachments are OK".

## LLM adapter

`LlmProvider { name; review(input): Promise<ReviewOutput>; generate(task): Promise<T> }`, with output validated by zod. `generate` runs a generic text-only `JsonTask {instructions, input, schema, jsonSchema}` (e.g. the expects-work classification): same prompt layout (instructions, input JSON, output format with the task's JSON Schema), same structured output (`--json-schema` / `responseJsonSchema`), corrective retry and error handling as `review`, no tools or images.
- `claude-cli` (`src/llm/claude-cli.ts`): `claude -p --output-format json --json-schema <ReviewOutput draft-07 schema> --no-session-persistence --strict-mcp-config [--model <claudeModel>]`, plus `--tools ""` (no tools) or, when attachments have an `imagePath`, `--tools Read --allowedTools Read --add-dir <image dirs>` so the model can view the images by path. Prompt on stdin, run from an empty temp cwd. Reads `structured_output` from the envelope (falls back to JSON inside `result`, code fences tolerated), zod-validates, retries once with a corrective prompt on invalid output, times out after `llmTimeoutMs` (default 180s), and surfaces stderr on failure.
  The caller passes the domain prompt as `review(input, { instructions })` (#20); `src/llm/prompt.ts` only wraps it with the input JSON, image paths and the output format.
  Only images are passed as files; other attachments must arrive as extracted `text`. Opt-in live test: `CA_LLM_IT=1 pnpm test llm.integration` (defaults to `--model haiku`).
- `gemini` (`src/llm/gemini.ts`): official `@google/genai` SDK, `models.generateContent` with `responseMimeType: application/json` + `responseJsonSchema` (the ReviewOutput schema minus `$schema`). Key from `GEMINI_API_KEY` (env or `.env` only; `config.local.json` rejects it), model from `geminiModel` / `CA_GEMINI_MODEL` (default `gemini-3.8-flash`, the latest stable Flash on the free tier as of 2026-10). Images (png/jpeg/webp/heic/heif) go inline as base64; the prompt lists their paths in order. 408/429/5xx and network errors retry with full-jitter exponential backoff (4 retries, 2s base, 60s cap, at least the server's `RetryInfo.retryDelay`); SDK retries stay off. Same corrective retry and zod validation as `claude-cli`; `llmTimeoutMs` bounds each HTTP attempt. `doctor` reports whether the key is set, never its value.
  Both providers run one shared contract test (`test/llm.contract.test.ts`) through their injected transports (command runner / SDK `fetch`). The live test runs Gemini only with `CA_LLM_IT=1` and `GEMINI_API_KEY`.
- `fake`: for tests (`respond` for `review`, `respondJson` for `generate`; without it `generate` fails like a provider error).

## Alerts and notifications

`Alert {key, level info|alert|panic, code, params, sentAt, mutedAt, muteReason}`. `sentAt` = delivered to Telegram; `mutedAt` = marked seen with the Telegram ✅ button (D15, D22, `muteReason` null) or muted automatically (`muteReason` `auto`, #51, D19; `superseded`, #52; `no_work_expected`, #61: reminders of a post that asks for no work, see Checks).

Replaced turn-ins (#52; `supersedeAlerts` in `src/checks/auto-ack.ts`, run in the same cycle step just before `autoAck`): when a submission's latest version was turned in again or has different attachments than an older version (compared on the payload's `turnedInAt` + `attachments`; a grade or a return alone doesn't count), every open `quality:<olderVersionId>…` alert (warn/panic, re-review, check by hand, failed review) is muted with `muteReason: superseded` (and `sentAt` when unsent). So the digest and the backlog only carry the latest turn-in's alerts; the new version is reviewed as usual and raises its own.

Auto-ack (#51, D19; `src/checks/auto-ack.ts`, a `run` cycle step after the quality reviews): an assignment is **resolved** when its submission is turned in (the `missing` bucket wins) and either returned or graded by the teacher, or has attachments and an `ok` latest LLM review of its latest version. For resolved assignments, `autoAck` mutes (`mutedAt` + `muteReason: auto`, and `sentAt` when unsent so it never goes out) the open alerts about the old state: `deadline:<id>:*` (untouched, due soon, missing, no due date), `comment:<id>` alerts of teacher comments posted before the latest turn-in, and `quality:<versionId>…` alerts of older versions. Never an alert created after the resolution (the ok review, or now for returned/graded) and nothing about the latest version. The backlog drops those items by itself (D17: resolved state). The cycle printout leaves out alerts muted in the same cycle; the console report and every Telegram digest end with "✔️ Closed automatically: N" (the report counts since `--since`, the digest since the previous digest, `telegram.json` `lastDigestAt`), and `report --all` marks muted alerts as acked / closed automatically. What an alert says is stored as a `code` plus JSON `params` (`AlertContent` in `src/store/types.ts`: `deadline.missing|due_soon|untouched_24h|no_due_date`, `comment.teacher`, `quality.review|unchecked|llm_failed`, `sync.session|drift`, and `text` for untranslated free text, which is also what alerts from before #49 became) and rendered at print/send time by `renderAlert` (D18).

Language and time (#49, D18; `src/i18n/`): every parent-facing string (alert texts, console report, Telegram digests, `/status` and other replies, help, the `telegram test` message, unreadable-attachment reasons) comes from a typed catalog, one object per language (`uk.ts`, `ru.ts`, `en.ts` implementing `Messages`), picked by `digestLang` (`CA_DIGEST_LANG`, `uk` default | `ru` | `en`). Plurals use `Intl.PluralRules` (`2 дні`, `5 днів`), titles are quoted «…» in uk/ru. Times are formatted with `Intl.DateTimeFormat` in `timeZone` (`CA_TIMEZONE`, IANA, default `Europe/Kyiv`, validated at load); the same zone drives the digest time and quiet hours (`zonedClock`). The LLM writes in `digestLang` (prompt `review.v5`, `locale`); text the LLM already wrote isn't translated again. Unreadable attachments carry a structured cause (`UnreadableCause`), rendered per language; the LLM still gets the English reason. Operator output (logs, `sync`, `doctor`) stays English.

Console digest (`src/notify/console.ts`, `report [--since 24h] [--all]`): one section per watched account (DB `watched` or in the config watch list), labelled by display name or the email's local part. Sections: 🔴 panics, 🟠 alerts, 📥 work turned in within the window with the merged verdict (latest `llm:*` CheckResult with its `summaryForParent`, else the heuristic verdict marked "heuristics only", else "not reviewed yet"; `unchecked` shows as "🔍 not checked automatically", and a reviewed one with unchecked parts adds "🔍 N parts not checked automatically"), 🔍 check by hand (`quality:<id>…:unchecked` info alerts, hidden when the same version has a `quality:<id>` warn/panic alert in the report), 📌 open debts (below), ℹ️ info, 🟢 upcoming (below). Alerts are resolved to an account through their key (`deadline:<assignmentId>…`, `quality:<submissionVersionId>…`, `comment:<commentId>`, `sync:<accountId>…`); anything else lands in "Other". The default window shows alerts created since `--since` plus every unsent one; `--all` shows everything. Muted alerts are left out of the default window (`--all` still shows them). The console never writes `sentAt`: that belongs to the Telegram notifier.

Open debts ("хвости", #48, D17; `src/checks/backlog.ts`): what a kid still owes, **computed from the current state** every time a report or digest is built, so a debt disappears by itself once resolved. One line per assignment (priority redo > missing > check by hand), oldest first:
- 🔁 **redo**: the latest fresh (non-baseline) teacher comment asks to redo/fix/attach (`isRedoRequest`) and the work wasn't turned in after it (`turnedInSince`). Age from the comment; ack id = its `comment:<id>` alert.
- ⏰ **missing**: not turned in (status `missing` wins; else the submission state) and marked missing or past due; materials and excused work are out. Age from the due date, else from the `deadline:<id>:missing` alert; a baseline item without a due date counts from its posting date, so old baseline items stay out. Ack id = `deadline:<id>:missing`.
- 🔍 **check by hand**: an unmuted `quality:<id>…:unchecked` alert of the latest version of a submission that is still turned in. Age and ack id from that alert.
A debt is forgotten `backlogForgetDays` (`CA_BACKLOG_FORGET_DAYS`, default 14) after it appeared. Marking its alert seen drops a check-by-hand debt (the parent checked it), but a redo or missing debt stays until the state resolves it (#63): it then shows as ✅ seen in Telegram. In `report` each line shows the kind, title, course, age in days and the details link (`authuser=<email>`), per kid after "check by hand"; in Telegram debts are problems of their assignment's line and card (below). A debt whose alert is listed in the same report/digest is left out of the block. The `run` printout and panic messages don't carry it. `/status` counts all of them. `due_soon` is not a debt: its panic covers it.

Upcoming (#53; `buildReport` option `upcoming: {days}`): a green, informational block per kid of work not turned in yet (by status and submission state; excused, `missing` and materials excluded) whose due date is later than a day from now (inside that, the `due_soon` panic covers it) and within `upcomingDays` (`CA_UPCOMING_DAYS`, default 14), sorted by due date, with due time (in `timeZone`), relative time, course and title, and in Telegram the details link. A live view recomputed every time: baseline items are listed too, no alert rows, nothing to ack. Shown in `report` (last block per kid), in every Telegram digest (a day with only upcoming work still gets a digest) and as a count in `/status`; an empty block is omitted.

Telegram (`src/notify/telegram.ts`, enabled when `TELEGRAM_BOT_TOKEN` and at least one chat id are set):
- `TelegramApi`: plain Bot API over `fetch` (`POST https://api.telegram.org/bot<token>/<method>`, JSON). The token comes from `TELEGRAM_BOT_TOKEN` (env / `.env` only; `config.local.json` rejects it) and is redacted from every error message. A 429 is waited out once (`retry_after`, ≤ 60s).
- Chats: `telegramChatIds` / `CA_TELEGRAM_CHAT_IDS`. `telegram link [--chat <id>]` calls `getMe` + `getUpdates` (no offset, so nothing is confirmed), lists the chats that messaged the bot and appends the chosen id to `config.local.json`. `telegram test` sends a test message to each linked chat. Groups work like private chats (negative ids; commands as `/status@<bot>` too); replies go to the chat that sent the command. When Telegram upgrades a group to a supergroup, a send fails with `parameters.migrate_to_chat_id` (and the group gets a `migrate_to_chat_id` service message): the notifier switches to the new id, resends, remembers `chatMigrations` in `telegram.json` (applied to the configured ids at start, so it also works with `CA_TELEGRAM_CHAT_IDS`) and rewrites `config.local.json` (`replaceTelegramChat`); `telegram test` does the same.
- Delivery: after each `run` cycle (`TelegramNotifier.afterCycle`, `sendCards`) every unsent, unmuted **panic** goes out at once as a standalone **card**, even in quiet hours; a fresh **teacher comment** (`comment:<id>` alert) too, but outside quiet hours. One card per assignment, showing all its open problems (unmuted alerts of the last 7 days plus its debt). Everything else waits for the **daily digest** at `telegramDigestTime` (`HH:MM` in `timeZone`, default 19:00): once per day in that zone, from that time on, outside quiet hours (a digest time inside the quiet window goes out when it ends, if still the same day). The digest shows every **open** alert (unmuted, created within the last 7 days), the ones not sent before marked 🆕, plus the open debts and upcoming work: an item stays in every digest until it is marked seen or resolved (auto-ack, turned in). Older alerts stay console-only. Alerts are marked `sentAt` once at least one chat got the message; on failure they stay unsent and are retried (the digest after 5 minutes).
- Navigable digest (#66, D22; views in `src/notify/telegram-views.ts`): HTML parse mode, everything escaped, inline keyboards. Alerts and debts are grouped **per assignment** (`ref` `a<assignmentId>`, or `x<alertId>` for other alerts not about one; resolved through the alert key: `deadline:` → assignment, `quality:` → submission version → assignment, `comment:` → comment → assignment). Sync alerts (`sync:` keys: lost login, parser drift) are not items: they are a ⚠️ banner line under the kid on the summary and at the top of the kid's list (open ones only; they close by themselves on the next successful sync). Free-text alerts (`code: text`, from before #49) get their tag from the key (`legacyTag`: `deadline:<id>:untouched_24h` → not started, `quality:<id>:unchecked` → check by hand, …; "sync problem" only for `sync:` keys, "notice" for unknown keys). Each problem gets a short tag (due soon / past due / not turned in / not started / teacher comment / needs rework / incomplete / check by hand / …) and a rank (🔴 0, 🟠 1, 🔵 2). Levels: **summary** (per kid: urgent count, open assignments, ✅ seen, upcoming; a button per kid, 🟢 upcoming, 🔄 refresh) → **list** (5 per page, one line per assignment: icon, the short title (leading/trailing dates and the separators they leave stripped, e.g. `08.10.2026-географія` → `географія`; titles that would then look the same, like `English. 09.10.2026` and `English. 12.10.2026`, keep their dates: `shortTitles`) linking the details page with `authuser=<email>`, then the date and the tags; number buttons open the card, ◀ ▶ page) → **card** (full title, course, due date, each problem with its detail, teacher comments and review notes as collapsible quotes; 🔎 Classroom, ✅ Seen, 🔄 Recheck when work is turned in, ⬅ Back). Seen assignments are crossed out with ✅ and sorted to the end of the list. A tap (`callback_query`, data ≤ 64 bytes, see `encodeAction`) is answered with a short popup at most and **edits the message in place**, so the chat doesn't scroll. ✅ Seen mutes every unmuted alert of the assignment and returns to the list page (a standalone card is edited in place). Each sent digest/card remembers its alert ids in `telegram.json` `views` (`<chatId>:<messageId>`, newest 200): a tap re-renders those alerts with their current state plus the current debts and upcoming work; a tap on a forgotten message says "out of date".
- Commands: the `run` loop's wait between cycles becomes `TelegramNotifier.idle`, which long-polls `getUpdates` (50s, `allowed_updates: ["message", "callback_query"]`) and sends the digest when it's due; on a polling error (network, 409 from a second poller) it logs and retries after 30s. Updates (messages and taps) from chats not in the list are dropped silently. `/status`: last `SyncRun` per watched account, open alerts (unmuted, last 7 days, or unsent) by level with the unsent count, and the number of open debts. `/digest`: sends the pending digest now ("Nothing pending." when there's nothing). Anything else starting with `/` gets the help text. At startup `setup()` reads the bot's username (`getMe`) and registers the command menu (`setMyCommands`) for the default scope and `all_group_chats`.

Manual triggers (#54, D20): `/refresh` (or the digest's 🔄 button) asks the `run` loop for a cycle now (sync → checks → digest): `idle` returns early (`manualPending`), the loop runs the cycle even in quiet hours, and afterwards a "fresh digest" (pending alerts, debts, upcoming, closed count, or "nothing new") goes to the asking chat only (the 🔄 button rewrites its own digest message instead, keeping the alerts it showed). At most one manual cycle per `refreshCooldownMin` (`CA_REFRESH_COOLDOWN_MIN`, default 5; a too-early `/refresh` gets the minutes left). While a cycle runs, `during()` keeps polling commands (10s long polls): `/status` etc. are answered, `/refresh` gets "already running" and the digest when it ends. A card's 🔄 Recheck button, `/recheck <Classroom link>` or `/recheck <assignmentId>` (resolved through `parseClassroomLink` → course and coursework ids → DB, watched accounts only) queues the assignment for the next cycle (which starts as soon as the cooldown allows): the cycle's sync gets `force` (the item's details are re-fetched and its submission files downloaded again, ignoring the file cache, `FetchOptions.force`), then `recheckAssignments` reviews the latest turned-in version again (`reviewSubmission(..., {force: true})`: new heuristic + LLM CheckResults, alert key `quality:<id>:r<n>`, alerting on warn/panic regardless of the previous verdict); once the new result is stored, the submission's older open quality alerts are muted as `superseded` (as in #52). A version that got its first review in that same cycle isn't reviewed twice. The asking chats get the verdict and the new alert's text. Read-only against Classroom: a recheck only reads. The update offset and the last digest day live in `<dataDir>/telegram.json`.

## Deployment

Phase 1: this laptop, `run` loop (default every 60 minutes, quiet hours).

`run [--once]` (`src/run/`): every `runIntervalMin` minutes (default 60) a cycle runs sync → `evaluateDeadlines` → `reviewSubmission` over `pendingQualityVersions` → prints a digest of the alerts raised in that cycle (alert id above the pre-cycle max). A failing step is logged and the next steps still run. Sync is an injected `SyncFn`; the CLI passes `playwrightSync(config)` (headless), the deadline lookback and the expects-work classifier (provider, `expectsWorkMaxPerRun`). `quietHours` (`HH:MM-HH:MM`, local time, may cross midnight, end exclusive) skips cycles; `--once` runs one cycle regardless. `<dataDir>/run.lock` holds `{pid, host, startedAt}` and is created exclusively; a lock whose PID is dead on this host (or unreadable) is stale and replaced. SIGINT/SIGTERM stops after the current step (no new reviews start); a second Ctrl-C exits at once. A lock with our own PID on this host is stale too (a restarted container often reuses the PID).

Phase 2: Docker (Playwright base image, `/profile` and `/data` volumes, `prisma migrate deploy` on start, non-root) on a microVM, with a noVNC `login` command for the hand login. The session must be created on Linux itself (a macOS profile can't be decrypted there). Risk: Google may re-verify a session that comes from a cloud IP. See [DEPLOY.md](DEPLOY.md).
