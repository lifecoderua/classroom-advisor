# Decisions

A short log of decisions. Newest at the bottom. Greenfield: breaking changes are fine and there's no backward compatibility.

### D1. No official API (2026-10)
Both the Classroom API (OAuth) and Apps Script under the kids' accounts were tested and are blocked by the school's domain policy. Access would need the domain admin, which is slow and wouldn't scale. **Revisit** if the admin grants it, since the API would replace most of the collector.

### D2. Never automate login
The kid accounts have passwords and no 2FA, but scripted logins trigger Google's challenges and are flaky. We reuse a **session that was logged in by hand**. When the session expires, the tool reports it and stops; a human logs in again.

### D3. Collector = dedicated Chrome profile + Playwright/CDP
Recent Chrome versions block automation on the default profile, so the collector uses its own `--user-data-dir` (`~/.classroom-advisor/chrome-profile`) with every kid account multi-logged-in. Accounts are selected with `authuser=<email>`.
Compared with a browser extension, this gives us control over scheduling, testability, and nothing for the kids to switch off. **Fallback:** an MV3 extension in a daily-use browser, reusing the same parsers (#16), if Google flags the automated profile.

### D4. Parse network data, not the DOM
Classroom's CSS is generated. RPC and init-data payloads are positional arrays, which is also fragile but changes less often. Parsers are isolated and tested on synthetic fixtures, and drift raises an alert.

### D5. SQLite + Prisma
Single user and small data. Prisma is used for its schema and migrations. Postgres only if we ever go multi-user.

### D6. Heuristics produce signals; the LLM decides
Zero attachments is often legitimate (lessons without homework, online tests). Heuristics feed signals into the LLM pass instead of panicking on their own. User-defined rules will come later.

### D7. LLM adapter: `claude -p` first, Gemini second
Use the local `claude` CLI (no API key to manage). Gemini by API key comes next because of its free tier. The provider can be swapped through config.

### D8. Privacy
Real data (captures, files, DB) stays only under gitignored `.data/`. Fixtures are synthetic. The repo is private. Personal use only for now. If this ever goes public, onboarding must explain the session reuse and that work is sent to an LLM.

### D9. Telegram right after the MVP
The MVP is data + minimal checks + console report. Telegram is the first notifier after that.

### D10. Call the internal read-only RPCs directly (2026-10-11)
Recon (#18) found that To-do and detail pages embed no data; it all arrives via `batchexecute` RPCs. Rendering pages and sniffing traffic works, but it's slow and fragile. So we open one page per account for the session tokens, then call the allow-listed read-only rpcids ourselves. The risk is an undocumented API whose positions and rpcids can change. That's why parsers sit behind `ParseDriftError`, fixtures are kept, and `recon` is there to re-learn the shapes.

### D11. First sync is a baseline; reminders have a lookback (2026-10-11)
The real To-do lists hold hundreds of old items, mostly lesson posts with no homework. Without a guard the first sync would raise ~290 `untouched_24h` / `no_due_date` alerts and send every old turned-in submission to the LLM. So the first successful sync per account only records a baseline (no events, no file downloads, no reviews, only the `missing` / `due_soon` panics for those items), and the two reminders apply only to items posted within `alertLookbackDays` (default 14). Items are flagged at creation, so a baseline interrupted by an expired session continues as a baseline next time.

### D12. Docker: log in inside the container, via noVNC (2026-10-11)
The image (#14) runs `run` with the Chrome profile and the data as volumes. A profile can't move from macOS to Linux: Chrome's cookie key lives in the macOS Keychain, while in the container Chrome uses its fixed "basic" key, so a copied profile looks logged out. So the image ships a `login` command (Xvfb + x11vnc + noVNC on loopback) where a human logs in by hand on the machine that will run the collector (D2 still holds). Google Chrome stable has no linux/arm64 build, so the browser is configurable (`CA_CHROME_CHANNEL=chromium` for Playwright's bundled build) and the image picks it automatically on arm64. The container defaults to Gemini (an API key in `.env`); `claude-cli` is an opt-in build arg plus `CLAUDE_CODE_OAUTH_TOKEN`.

### D13. Sweep private comments every sync; alert on fresh teacher comments (2026-10-11)
Teacher comments ("redo", "attach the photo") are high-signal, but a new comment doesn't reliably change the submission's update time, so fetching comments only for re-fetched items would miss some (5 of 24 commented submissions on the real data). `sLc6hf` accepts 100 submission keys per call, so every sync sweeps all of them for ~2 calls per account. Comments that predate the baseline (or arrive in it) are stored silently; every later teacher comment raises an `alert` with its text in the local digest. Student comments only emit `comment.new`.

### D14. Teacher comments re-queue a review; redo requests are panics (2026-10-11)
Reviews run once per submission version, but a teacher's "переробити" / "прикрепи фото" usually arrives after the review, often with no new version. So a fresh teacher comment re-queues one more review of the latest version (watermark `CheckResult.throughCommentId`, so one comment = at most one re-review), and that re-review alerts under its own key (`quality:<id>:c<commentId>`) only when the verdict got worse, so the parent doesn't get the same verdict twice. A keyword list (uk/ru/en word-start stems) rather than the LLM decides whether the comment alert is a `panic`: it fires at sync time, before any review, and needs no provider. False positives are cheap (one panic about a real teacher comment); the LLM verdict is floored at `warn` while the request is open. Baseline versions are still never reviewed (D11; their files aren't downloaded), so a redo comment on one only raises the comment alert.

### D15. `Alert.sentAt` means "delivered to Telegram"; the console stays read-only (2026-10-11)
There's one push channel, so delivery state is one column, not a per-channel table. Telegram owns `sentAt`: it sets it after a successful send (panics right after the cycle, the rest in the daily digest), and the console `report` and the `run` printout never write it, so they keep working the same with or without Telegram. Without Telegram nothing marks alerts sent and the console shows unsent ones as before. `/ack <id>` sets a separate `mutedAt` (plus `sentAt` if unset, so a muted alert never goes out); muted alerts drop out of digests, `/status` and the default console window. Telegram sends only alerts from the last 7 days, so enabling it on an old DB doesn't replay history. **Revisit** with a per-channel delivery table if a second push channel (email, etc.) appears.

### D16. Skip what we can't read, but say so: "not checked automatically" (2026-10-11)
Some work can't be checked automatically: legacy `.ppt`/`.doc`, audio and video, files too large to download, failed downloads, scans without text, external test platforms, or requirements the LLM can't judge. These are not problems with the child's work, so they must not raise a warn, and they must not pass silently as `ok` either. Each such part is reported with a reason as "check by hand" (#43): unreadable attachments are listed (the readable rest is reviewed normally), the LLM returns what it can't verify as `unverifiable: [{what, why}]`, and the digest shows them in a separate low-noise section, one per submission version, or inside the warn/panic alert when there is one. When nothing attached is readable, the LLM isn't called and the verdict is `unchecked` (unless the heuristics warn). If every cause is temporary (not downloaded yet, a download error other than "too large"), the version is retried up to 3 times before it stays `unchecked`; the check-by-hand alert waits for the last attempt.

### D17. Open debts are derived from current state, acked through their alert (2026-10-11)
The parent wants unresolved things ("хвости") repeated in every digest until they're done (#48): open teacher redo requests, missing/overdue work, "check by hand" items. We compute them from the current DB state each time a digest or report is built (`loadBacklog`) instead of storing debt rows or re-sending alerts: a debt then resolves itself as soon as the sync sees the work turned in again, with no extra state to keep in sync. Ack reuses `/ack`: every debt points at the alert that announced it (`comment:<id>`, `deadline:<id>:missing`, `quality:<id>…:unchecked`), and a muted alert drops the debt. Debts are forgotten `backlogForgetDays` (default 14) after they appeared (due date, comment, or alert time), which also keeps baseline items out: they count from their due date (or posting date), so years-old missing work doesn't flood the first digests. Only fresh (non-baseline) teacher comments count as redo requests, like their alerts (D13). `due_soon` is not a debt (it's a panic and in the upcoming list). One line per assignment; a debt whose alert is already in the same message isn't repeated.

### D18. Alerts store code + params; rendered per language at send time (2026-10-12)
The parent reads Ukrainian (or Russian), and the language must be switchable (#49). Rendering at raise time would freeze each alert in the language of the day it was raised, and the language couldn't change for the backlog or old alerts. So `Alert` stores a `code` and JSON `params` and every output (console, Telegram, `check`) renders it with the configured `digestLang` and `timeZone` through a small typed catalog (no i18n library: one object per language implementing one interface, so a missing string is a type error). Free text from the LLM is generated in `digestLang` in the first place (prompt `review.v4`), so it's stored as is; teacher comments are quoted as written. Existing rows were migrated to the `text` code (their English text, shown unchanged): greenfield, no re-rendering. Time zone (`CA_TIMEZONE`, default Europe/Kyiv) is explicit instead of the process zone, because the container runs in UTC.

### D19. Auto-ack resolved work through `mutedAt` with a reason (2026-10-12)
Once the work is turned in with files and reviewed `ok`, or returned/graded by the teacher, the parent shouldn't have to `/ack` the deadline, redo and old-version alerts by hand (#51). We reuse `mutedAt` (so every existing filter — digests, `/status`, backlog — already does the right thing) and add `Alert.muteReason` (`auto`; null = by hand) so `report --all` can tell them apart and digests can say "Closed automatically: N". It runs as a cycle step over the current state, like the backlog (D17), rather than at the moment a review finishes, so returned/graded work and late reviews are covered by the same rule. It never mutes alerts created after the resolution or anything about the latest version: a newer problem stays visible.

### D20. Manual triggers go through the `run` loop (2026-10-12)
`/refresh` and `/recheck` (#54) don't open their own browser: the collector profile can only be used by one Chrome at a time and a second context would race the scheduled cycle. Instead the notifier asks the loop for a cycle (the wait between cycles returns early) and keeps answering commands while a cycle runs, so a request during a cycle gets "already running" plus the result. Rechecks ride on that cycle: sync re-fetches the item ignoring caches, then a forced review stores a new CheckResult and supersedes the old alerts. One manual cycle per 5 minutes (configurable) keeps a tapping parent from hammering Classroom; manual cycles ignore quiet hours because someone is clearly awake.

### D21. Lesson posts without homework: lazy LLM classification per version, skeleton cache (2026-10-12)
Most posts are lesson-schedule entries (`assignment` kind, no due date, a call invite as the description), and every `untouched_24h` reminder in the real DB was on one of them (#61). Title rules can't separate them, because homework can sit in the title, the description or an attachment, and teachers edit posts later to add it. So an LLM decides `yes | no | unclear` per `AssignmentVersion`: each content state once, and an edit (a new version) is classified again. It runs lazily, only when a reminder is about to fire, so baseline and old posts never cost a call, and it's capped per run (`expectsWorkMaxPerRun`, default 20) so an existing DB doesn't burst. Instead of a hand-written template library, a **skeleton cache** reuses an earlier LLM `yes`/`no` of the same account when the normalized text (URLs → host, times, dates and digit-bearing words masked) and the attachments hash the same: a weekly invite costs one call. URLs keep their host so a call link and a worksheet link don't collide, and `unclear` is never reused. `no` only suppresses the reminders (`untouched_24h`, `no_due_date`); the panics (`missing`, `due_soon`) only fire on due-dated work and stay untouched. `unclear` and failures keep today's behavior. Already-open reminders are muted with reason `no_work_expected`, and that reason is silent: it's not counted as "closed automatically", so these posts stay out of the digest entirely. A muted reminder comes back if a later version fires it again. **Revisit** if the cache misses too often (topics that change in words, letter-only passcodes) or a `no` turns out wrong in practice.
Homework often sits only in the teacher's attachment (a Math post says "Самостійно розв'язати приклади" and the tasks are in a pptx), and sync used to download files only for turned-in work (8 of 374 teacher materials had content). So sync now prefetches the text-bearing materials of the classifier's candidates (open, non-baseline, within the lookback, unclassified; capped per account and sync by `expectsWorkMaxPerRun`), and classification waits for that download. The prompt (`expects-work.v2`) treats any instruction to do something as `yes`, even a short one with the details in an attachment, and asks for `unclear` rather than `no` when an attachment can't be read. On top of the prompt there is a deterministic safety net: a `no` is stored as `unclear` whenever a material other than a call link has no readable text. A wrong `no` hides homework; a wrong `unclear` only costs a reminder. "Recommended" homework ("рекомендовано для виконання вдома", "за бажанням") is treated as required everywhere: it is `yes` for the classifier, and the review prompt (`review.v5`) expects it done fully.
